# 控制链路修复与验收记录

基线：STM32F427 / CAN2 DJI 0x201～0x208 / Keil ARMCC 5.06。底盘运动学、任务10ms周期、击打角度表、PID增益和遥控映射保持原标定；修复不包含IMU、看门狗、物理急停、DM闭环、CMake或H723移植。

## 修改后的运行约定

| 项目 | 行为 | 限制 |
|---|---|---|
| 启动 | 设备初始化返回状态给main；启动任务以28级创建CAN mutex和全部业务资源，正常创建阶段不阻塞、不让出CPU，成功后删除自身 | RC27/底盘26/击打25低于启动任务；业务模块不查询启动状态，创建失败返回给编排层统一处理 |
| CAN提交 | 每条总线独立静态mutex，最多等待1 tick；标准、扩展和Keil中旧发送函数均进入BSP；保护邮箱选择至TXRQ提交 | ISR、关中断、BASEPRI非零和调度器未运行时拒绝发送；不等待总线发送完成，不忙等重试 |
| 遥控失控 | failsafe、frame-lost、坏帧或接收超时令底盘失能、击打清零；恢复要求SF为UP、SWD非DOWN | 首个安全帧只确认恢复，后续新帧才允许操作；若覆盖队列跳过确认帧，保持安全按键状态直到击打任务确认 |
| 位置反馈 | CAN每帧整数累计，首个真实反馈累计为0；任务读取一致性快照并做浮点换算 | 相邻反馈间必须小于半圈；任意短暂丢帧造成的圈数丢失无法完全检测或补回 |
| 位置故障 | 半圈歧义、累计溢出或反馈间隔超过100ms使位置无效；任一击打位置电机故障锁定整个0x1FF组 | 重新来帧不会解锁。摆回已知机械起始位置后完整重启；没有自动绝对零点识别 |
| 恢复回零 | 遥控失控期间继续累计有效反馈，重新使能时从实际位置生成平滑回零目标，并清PID历史 | 0x205单独离线只清其电流及PID；不重新定义三个击打位置电机原点 |

发送接口返回OK只代表HAL已提交邮箱，软件缓存清零也不代表电机已收到停机帧。发送失败在BSP中计数，下一控制周期只提交最新输出。

## 上板验收表

连续运行观察，避免长时间断点打断反馈链路；调试停顿可能导致位置故障，恢复测试前按起始位置重新上电。每次测试记录固件版本、负载、目标、反馈、提交结果和实际时延，不预填未测数据。

| 用例 | Keil观察量 | 通过条件 / 待填写结果 |
|---|---|---|
| 上电与时间 | `g_startup_error`、业务任务句柄、`uwTick`、FreeRTOS `xTickCount` | 启动错误为0，任务创建成功，两种tick均前进；待实测 |
| 首帧与在线 | `s_dji_motor[5..7].feedback.online/position_valid/total_ecd/last_update_ms` | 未收帧不得建立位置原点；收到首帧累计0，随后时间戳持续更新；待实测 |
| 准备位与三档 | `s_hit_state`、`s_hit_motor[0..2].target_angle/total_angle/angle_pid.get` | 首次安全确认不动作，随后平滑到准备位；三档目标和方向一致，无持续振荡；待实测 |
| 断无线链路 | `s_rc_recovery_wait`、`s_hit_state`、两组发送电流 | 接收机仍发串口帧时也要停止；SF一直按着或SWD开启时不能恢复；待实测 |
| 反馈断线 | 三个位置反馈的帧龄、`position_valid`、`s_hit_state`及0x1FF数据 | 超过100ms后下一正常控制周期提交零电流；恢复反馈仍锁定，完整重启才恢复；待实测 |
| CAN负载与抢占 | `s_tx_stats[0..1]`或`BSP_CAN_GetTxStats()`、CAN抓包 | `0x200/0x1FF`数据不串帧；统计BUSY/error；验证目标RTOS的优先级继承和最大等待；待实测 |
| 周期与资源 | 任务高水位、调度/执行时间、堆余量 | 记录实际10ms周期最大偏差、最长执行时间和最小栈余量；待实测 |

Watch表达式需要展开具体下标，例如`s_dji_motor[5].feedback.total_ecd`；表中的`[5..7]`不是合法表达式。`online`仅表示收到过反馈，实时在线还要检查帧龄；`s_hit_state`数值为IDLE=0、PUT_ANGLE=1、RETURN=2、WAIT_REMOTE=3、POSITION_FAULT=4、DISABLE=5。RETURN结束表示目标轨迹已到准备位，并不独立证明机械反馈已到位，仍需比较目标与实测位置。

启动错误码：1=设备/CAN初始化，2=TX mutex，3=启动任务，4=业务队列，5=业务任务。硬件失败不会通过软件自动重试启动。

启动依赖已调整为`main/start_task -> 业务任务创建接口 -> RTOS/设备层`。三个创建接口返回`Task_CreateResult_t`，任务创建失败会释放本次创建的队列；设备初始化返回bool给main。业务任务不包含`start_task.h`，不调用启动状态查询或启动故障函数。启动优先级28必须始终高于全部业务任务，正常创建阶段不能增加阻塞等待；后续调整任务优先级或启动流程时需重新验证此条件。

当前上板时延、任务周期、栈余量和机械稳定性均待实测；主机测试和构建通过不能替代这些结果。
